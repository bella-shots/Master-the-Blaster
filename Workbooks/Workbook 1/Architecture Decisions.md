# Architecture Decisions

> Source: `Phase_1_Product_Architecture_Google_AI_Studio_AUTONOMOUS_REVISED.xlsx`

| PHASE 1 — ARCHITECTURE DECISION RECORD |  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ID | Decision area | Decision to make | Preferred direction | Reason / boundary | Human gate | Evidence required | Status |
| A1 | Application runtime | What application runtime/framework will be the implementation foundation? | React + TypeScript + Vite/Tailwind (or the existing AI Studio-compatible client runtime) as the primary application runtime; do not assume a production server is required. | The runtime must work with the selected no-billing hosting architecture. Existing Express/server.ts may remain temporarily during proof; it is not approved as a mandatory production backend. | Only if the selected runtime cannot satisfy a required capability without a billing-dependent server. | Runtime builds and runs in the zero-billing proof; responsibility boundaries documented. | Gate — Open |
| A2 | Visual editor | What engine powers the full website builder? | GrapesJS or another mature open-source visual editor that demonstrably supports the required capability set. | Do not build drag/drop/editor internals from scratch in 2 days. Licensing/cost must remain compatible with the ₹0 invariant. | Only if engine choice requires user approval/license clarification. | Capability matrix mapped to engine features and license. | Open |
| A3 | Structured data | Where does application state live? | Firestore for users, projects, permissions, finance/HR records, pages and metadata. | One authoritative owner per entity; avoid giant opaque blobs. Direct web access must be protected by Firebase Auth + Firestore Security Rules. | No | Schema ownership map + Security Rules design. | Open |
| A4 | File storage | Where do uploaded Excel/PDF/image files live? | Google Drive via supported API/integration; store Drive file metadata/IDs in Firestore. | Avoid mandatory Firebase Storage/Blaze dependency. Drive OAuth must be tested or its exact integration boundary documented. | Yes if Drive OAuth/permissions require user action. | Successful authorized Drive access or documented tested integration boundary. | Open |
| A5 | Authentication | How are users identified? | Firebase Auth / Google identity approach supported by the selected client runtime. | No anonymous privileged access. Sensitive modules require authenticated identity mapped to an application role. | Yes if OAuth/configuration requires user action. | Authenticated user can be mapped to role and Security Rules can consume the identity. | Open |
| A6 | Email | How are MOM emails sent? | Gmail API or another Google-supported mail mechanism, subject to proving the required user-authorized and/or unattended behavior without a mandatory billing-dependent backend. | Do not introduce paid transactional email. Do not assume browser-only Gmail automation satisfies unattended MOM sending until verified. | Yes if Google OAuth consent is required; also stop for an unresolved unattended-send architecture decision. | Controlled test email or documented proof boundary showing exactly what is and is not possible. | Gate — Open |
| A7 | Backend | Where do server-side mutations/business rules execute? | Primary candidate: no mandatory backend for core CRUD; use Firebase Auth + Firestore Security Rules for client-accessible data. Retain existing Express/server.ts temporarily only as an implementation artifact while the zero-billing proof determines whether any server-side capability is genuinely required. | Do not introduce Cloud Run/Cloud Functions/App Hosting merely to preserve the existing Express boundary. Any required server-side secret, unattended job, or privileged API must pass the zero-billing gate. | Yes if a required capability cannot be implemented without a server-side service. | Mutation/security boundary diagram + proof of each required server-side capability or documented client-side replacement. | Gate — Open |
| A8 | Hosting | Where is the app deployed? | Primary candidate: Firebase Hosting static SPA on the no-cost Spark path. Cloud Run and Firebase App Hosting are rejected under the no-billing invariant. | Firebase documentation currently states Firebase Hosting offers a no-cost tier with no billing account required for small deployments; App Hosting and Cloud Run require billing. Verify current eligibility/quotas during the proof. | Yes if deployment authorization or project setup requires user action. | Hosting proof: deploy/test SPA without linking Cloud Billing; record quota/limit evidence. | Gate — Open |
| A9 | Permissions | Where is authorization enforced? | For direct web access, Firebase Authentication + Firestore Security Rules are the primary enforcement boundary; any server/API boundary must add its own authorization checks. UI visibility is supplementary only. | Never rely only on hidden UI controls. Server client libraries bypass Firestore Rules, so any privileged server path must have explicit IAM/auth checks. | No | Permission matrix + unauthorized read/write tests for each sensitive module. | Open |
| A10 | Builder persistence | How is page/editor state saved? | Persist structured page metadata/editor state in Firestore; store large assets separately in Google Drive where appropriate. | Reload must reproduce the saved page. Persistence must remain compatible with the no-billing architecture. | No | Save → reload → identical state test. | Open |
| A11 | Cost invariant | What happens if a chosen service requires paid billing? | STOP. Do not enable Cloud Billing/Blaze or accept a paid dependency. Redesign around a no-billing alternative unless the user explicitly changes the invariant. | The user's financial authorization controls any exception. 'Free quota' behind a mandatory billing account does not satisfy this invariant. | Yes | Explicit proof that the selected production path does not require Cloud Billing; otherwise a documented STOP decision. | Gate — Open |
| A12 | Zero-Billing Architecture Proof | Can the complete required application operate under the no-billing invariant? | Prove six boundaries independently: Firebase Hosting, Firebase Auth, Firestore + Security Rules, Drive, Gmail, and Gemini. Do not finalize architecture until the proof is complete. | A hosting free tier alone is insufficient. Drive/Gmail/Gemini behavior, security, secrets, quotas and unattended requirements must also be tested or explicitly bounded. | Yes if any proof requires account authorization, unresolved product decision, or billing. | ZBA-01 through ZBA-07 evidence with PASS/FAIL/OPEN status and exact remaining human decisions. | Not Started |
